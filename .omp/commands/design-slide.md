Read `.omp/skills/presentation-design/SKILL.md` and the applicable final references before acting: `.omp/skills/presentation-design/references/design-principles.md`, `.omp/skills/presentation-design/references/reference-analysis.md`, `.omp/skills/presentation-design/references/anti-slop.md`, `.omp/skills/presentation-design/references/slide-archetypes.md`, `.omp/skills/presentation-design/references/visual-qa.md`, and `.omp/skills/presentation-design/references/human-editing.md`.

Use only project-local presentation paths: the production slide is `presentation/decks/current/index.html`; static assets belong below `presentation/`; review state is `presentation/review/overrides.json` and `presentation/review/feedback.jsonl`; the deck analysis lives in `presentation/decks/current/DESIGN_DNA.md`. An explicit user-selected mode always wins. If no mode is stated, use **RECONSTRUCT** only for a requested reproduction of a supplied slide; use **EXTEND** for a new topic or new slide. A supplied reference by itself never selects the mode.

1. Inspect the requested slide and enough existing deck material to extract its Design DNA. Create or update `presentation/decks/current/DESIGN_DNA.md` before writing slide HTML, including a target **Slide plan**: its one-sentence message, reader questions and reading path, intended archetype, visual/diagram roles, topology, visual count, and relevant production constraints. In **RECONSTRUCT**, record the reference-controlled topology and visual count alongside its anchors, proportion, crop, type hierarchy, color roles, and whitespace; reproduce that recorded composition rather than having the message-led Slide plan select it. In **EXTEND**, use existing deck DNA together with the message to select topology and visual count; treat any reference only as visual-language evidence—not as a scene graph to copy—and record the observed canvas, anchors/margins, typography and color roles, spacing rhythm, surface/line/connector semantics, image treatment, and deck furniture that the new slide will preserve.
2. Implement the slide on the fixed 1600 × 900 canvas with stable semantic `data-layer-id` values. Keep a primary image’s outer `image-frame` separate from its inner `img`. In **EXTEND**, let the message and Slide plan select the reading path, density, silhouette, visual count, and diagram topology under the deck DNA: do not impose a left-title/right-image layout, one-visual composition, hero visual, or fixed columns. Multiple diagrams are valid when each answers a distinct reader question and their relationship is explicit. In **RECONSTRUCT**, reproduce the reference-recorded reading path, density, silhouette, topology, and visual count unless a direct user edit overrides them.
3. Honor pending structured feedback and direct geometry in `presentation/review/overrides.json`; user geometry outranks inferred layout. Do not invent a second visual system or decorative filler.
4. Keep editor-only/reference-overlay behavior behind edit mode. For every changed slide, use the actual browser’s production resource inspection—not source inspection—to confirm that its production URL loads no reference, editor, Moveable, review/feedback, API, or remote-runtime dependency, and displays no editor UI, toolbar, comments, or controls.
5. For every changed slide, render and visually inspect `presentation/decks/current/index.html#slide-N` in production and `presentation/decks/current/index.html?edit=1#slide-N` in edit mode. In edit mode, use the previous and next controls to navigate away from and back to the changed slide when those neighbors exist; verify the current-slide indicator, target layers, persisted geometry and image crop, feedback and History state, and the correct local-reference state on every visited slide. Then render and inspect the whole deck through production navigation in published order. Report the mode; Design DNA evidence and Slide plan decisions; files changed; the browser resource-inspection result; and the production, edit-switch, and ordered deck visual-QA results.
